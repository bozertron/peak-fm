# Peak — Commerce

**Status:** Specification. Not yet implemented. **Last updated:** 2026-09-18
**Decision:** Stripe Connect behind a thin internal provider seam.

## 1. Why a seam

Four surfaces move money, and they do not move it the same way:

| Surface | Shape |
|---|---|
| Buy | one-off marketplace payment, buyer → seller, Peak takes a fee |
| Sell | the same transaction from the other side, plus payouts |
| Rent | a deposit, then **recurring** collection on a schedule |
| Trade | often **no money at all**, or money as one leg of a barter |

Trade is the reason for the seam. Forcing a barter leg through a card rail
would distort the product. The seam lets a Trade settle with zero payment legs
while Buy settles with one.

## 2. The interface

```ts
// lib/commerce/provider.ts — TO BE IMPLEMENTED (PEAK-230)
export interface PaymentProvider {
  readonly name: string

  /** Seller onboarding — KYC, payout details. Returns a hosted URL. */
  createSellerAccount(userId: string): Promise<{ accountRef: string; onboardingUrl: string }>
  getSellerStatus(accountRef: string): Promise<{ chargesEnabled: boolean; payoutsEnabled: boolean }>

  /** One-off purchase. Idempotent on `orderId`. */
  createPayment(input: {
    orderId: string
    amountCents: number
    currency: string
    buyerId: string
    sellerAccountRef: string
    feeCents: number
  }): Promise<{ providerRef: string; clientSecret: string }>

  capturePayment(providerRef: string): Promise<{ status: string }>
  refundPayment(providerRef: string, amountCents?: number): Promise<{ status: string }>

  /** Recurring collection for a rental auto-pay contract. */
  createSubscription(input: {
    agreementId: string
    amountCents: number
    currency: string
    cadence: 'weekly' | 'biweekly' | 'monthly'
    startAt: Date
    endAt?: Date
    payerId: string
    sellerAccountRef: string
  }): Promise<{ providerRef: string }>

  cancelSubscription(providerRef: string): Promise<{ status: string }>

  /** Verify and normalise an inbound webhook. Signature check is mandatory. */
  verifyWebhook(rawBody: string, signature: string): Promise<ProviderEvent>
}
```

`order.providerRef` / `providerName` and `autopay_contract.providerRef` /
`providerName` are the join between Peak's records and the provider's.

## 3. Stripe Connect mapping

| Peak | Stripe |
|---|---|
| seller account | Connected Account (Express) |
| `createPayment` | PaymentIntent with `application_fee_amount` + `transfer_data.destination` |
| `capturePayment` | PaymentIntent capture |
| `createSubscription` | Stripe Billing Subscription on the connected account |
| `verifyWebhook` | `stripe.webhooks.constructEvent` |

Separate charges and transfers, not destination charges, so a refund does not
have to claw back a completed payout.

## 4. Non-negotiable rules

1. **The database is the record of intent; the provider is the record of fact.**
   Never infer payment status from Peak's own tables — reconcile from webhooks.
2. **Idempotency everywhere.** `createPayment` keys on `order.id`. A retried
   network call must never create a second charge.
3. **Webhook signatures are verified.** An unverified webhook is discarded and
   logged, never processed.
4. **No secret reaches the client.** Only `clientSecret` crosses, and only to
   the buyer it belongs to.
5. **Commerce runs inside the thread.** A `message.kind = 'checkout'` carries
   the order reference in `payload`; `order.threadId` points back. The receipt
   and the conversation never drift apart.
6. **Auto-pay needs both signatures** before `active` may be true.
7. **`commerce.checkout` and `commerce.autopay` are feature flags.** Both ship
   disabled. An operator opens them per market without a deploy.

## 5. Tax and the Accounting Package

The provider reports what the money did. It does **not** decide tax treatment.

`accounting_record` is generated by Peak and frozen. The research-validated
relief field is governed by one constraint:

> `reliefNotes` may not be populated unless `researchSources` is non-empty and
> `confidence` is explicitly set.

A package that cannot cite a source states that on its face. This is research
output presented as research — never advice, and never an assertion Peak cannot
back.
